# XIV 地牢地图随机生成设计方案

> 状态：提案
>
> 适用范围：当前 32×32 地图、5 层普通楼层加 1 层最终 Boss 的垂直切片；后续扩展到 4 个大关时沿用同一套生成接口。

## 1. 设计结论

地图不再被视为一块只包含“墙”和“地板”的随机噪声，而是先生成一个由房间节点和过道边组成的连通图，再把这个图落到 32×32 网格上。

最终结构满足以下关系：

```text
房间（节点） ── 过道（边） ── 房间（节点）
       └────── 可选的额外过道，形成少量环路 ──────┘
```

- 房间分为小房间和大房间两种尺寸。
- 过道是连接两个房间的 1 格宽通路，默认不产生没有终点的死胡同。
- 所有房间必须从入口房间沿 4 方向移动到达。
- 出口放在距离入口较远的房间中；特殊敌人和 Boss 优先放在大房间中。
- “房间/过道”是地图布局语义，不直接扩充当前 `TileKind`。移动、寻路和存档仍以 `tiles` 为最终地形来源。

推荐的最终方案是自定义“房间放置 + 房间图连接”生成器。现有 `rot.js` `Digger` 可以作为过渡方案继续使用，但不作为长期的地图结构来源，因为它没有把过道、房间类型、房间角色和连接关系完整暴露给游戏逻辑。

## 2. 当前实现与需要解决的问题

当前 `src/world/generate.ts` 的流程是：

1. 用 `rot.js` `Digger` 在全图挖出地板。
2. 从 `getRooms()` 读取房间矩形。
3. 入口和出口按房间中心选择。
4. 敌人、特殊敌人和物品只在房间矩形内随机放置。
5. 其他系统只看到 `wall`、`floor`、`entrance`、`exit` 四种地块。

这套实现可以快速形成可玩的地图，但存在几个结构性问题：

- 房间和过道在数据上没有区别，无法可靠地表达“某个对象位于过道”或“某个房间是 Boss 房”。
- 房间目前没有大小分类，也没有入口房、出口房、目标房等角色。
- 地图生成没有显式的连通性验证，主要依赖 `Digger` 的行为。
- 出口、敌人和物品的放置规则与地图结构耦合在一个函数中，后续加入商店、事件房或大关主题时会变得难以维护。
- 测试只检查地图有地板、入口和出口，没有检查所有地板是否从入口可达，也没有检查房间数量和尺寸分布。

## 3. 地图布局模型

### 3.1 网格与边界

- 地图尺寸继续使用 `MAP_W × MAP_H`，当前为 32×32。
- 外围一圈固定为墙，实际布局区域为 `x=1..30`、`y=1..30`。
- 房间与地图边界之间至少保留 1 格墙；生成器不得从边界挖出通路。
- 普通移动使用 4 方向，因此连通性验证也必须使用 4 方向。8 方向只继续用于现有攻击距离和地形路径规则。

### 3.2 房间

房间使用轴对齐矩形表示。矩形内部全部是房间地板，房间之间默认至少隔 1 格墙。

| 类型 | 宽度 | 高度 | 典型用途 |
| --- | --- | --- | --- |
| 小房间 | 4–6 格 | 4–5 格 | 普通战斗、普通物品、路线过渡 |
| 大房间 | 7–10 格 | 6–8 格 | 特殊敌人、出口、事件、多个敌人 |
| Boss 大房间 | 10–12 格 | 8–10 格 | 最终 Boss；属于大房间的特殊尺寸 |

普通楼层的目标分布：

- 房间总数：7–9 个。
- 大房间：2–3 个。
- 小房间：其余房间。
- 房间占可通行地块的主体，过道负责连接和延伸路线。

前期垂直切片先使用单独的“基准层”配置，不直接采用上述普通楼层规模：房间总数为 3–5 个，固定包含 1 个大房间和至少 2 个小房间，并由至少 3 个房间组成基础回路。回路可以覆盖本层更多房间，也允许在回路内部增加穿行过道。具体拓扑、空间布局和验收规则见 [`baseline-floor-template.md`](baseline-floor-template.md)。

Boss 楼层可减少房间总数到 5–7 个，但必须保留 1 个 Boss 大房间和至少 2 个用于战斗前准备的普通房间。

每个房间还应包含以下布局信息：

```ts
type RoomSize = 'small' | 'large';
type RoomRole = 'entrance' | 'normal' | 'objective' | 'exit' | 'boss';

interface RoomLayout {
  id: number;
  size: RoomSize;
  role: RoomRole;
  left: number;
  top: number;
  right: number;
  bottom: number;
  centerX: number;
  centerY: number;
}
```

### 3.3 过道

过道是连接两个房间的通路，不把房间内部的地板计为过道。

- 默认宽度为 1 格。
- 过道从一个房间边界进入房间，不能只挖到房间外墙而不进入房间。
- 过道可以经过已经挖出的过道，从而形成环路，但不能穿过第三个房间的内部。
- 普通地图允许少量额外连接；推荐在最小连通树之外增加 1–2 条过道，形成 15%–25% 的环路机会。
- 过道不追求全部笔直。优先使用带一个转角的 L 形路线；过长时允许两个转角，但避免连续超过 16 格的单一路段。

```ts
interface CorridorLayout {
  id: number;
  fromRoomId: number;
  toRoomId: number;
  cells: { x: number; y: number }[];
  width: 1;
}
```

## 4. 生成流程

### 第 0 步：建立独立随机流

输入仍为 `seed` 和 `floorNumber`。生成过程必须完全由它们决定，同一个输入得到完全相同的地图。

建议把随机过程拆成几个派生种子或随机阶段：

- `objectiveSeed`：决定楼层目标。
- `layoutSeed`：决定房间位置、大小和过道。
- `contentSeed`：决定敌人、物品和房间内容。

这样，调整敌人数量不会意外改变房间布局，也方便对某个地图种子复现问题。实现上可以继续使用 `rot-js` 的 RNG，但应在每个阶段显式设定派生种子，避免所有逻辑共享一个不可见的随机游标。

### 第 1 步：选择楼层布局配置

楼层目标模板同时提供内容规则和布局参数。布局配置至少包含：

```ts
interface MapProfile {
  templateId: 'baseline' | 'findExitBranches' | 'boss';
  roomCount: [number, number];
  largeRoomCount: [number, number];
  loopRoomCount: [number, number];
  corridorLoopChance: number;
  chordChance: number;
  requireLargeObjectiveRoom: boolean;
  bossRoom: boolean;
}
```

建议的初始配置：

| 任务模板 | 地图模板 | 房间数 | 大房间数 | 主要约束 |
| --- | --- | --- | --- | --- |
| 前期基准层 | `baseline` | 3–5 | 至少 1 | 至少 3 个房间组成回路，可增加中穿过道，入口位于回路房间 |
| 找到出口 | `findExitBranches` | 固定 6 | 1–2 | 固定 3 房间回路 + 3 条终端支线，目标入口在其中一个终端房 |
| 击败 N 个敌人 | `baseline` | 3–5 | 至少 1 | 直接使用基准层，只调整普通敌人数量和分布 |
| 击败特定敌人 | `baseline` | 3–5 | 至少 1 | 直接使用基准层，特殊敌人在大房间或目标房 |
| 最终 Boss | `boss` | 5–7 | 至少 2 | 最大房间为 Boss 房，且有准备路线 |

任务模板必须在生成房间之前选择 `templateId`。不能先生成一张普通地图，再根据任务类型临时增删房间或补挖支线。`findExitBranches` 的具体拓扑见 [`find-exit-map-template.md`](find-exit-map-template.md)。

### 第 2 步：放置房间

1. 按配置随机决定房间数量和大房间数量。
2. 先放置大房间，再放置小房间，避免小房间抢占关键空间。
3. 随机生成矩形尺寸和坐标。
4. 拒绝以下候选房间：
   - 越过地图边界或破坏外围墙。
   - 与已有房间重叠。
   - 与已有房间相邻，导致两房间之间没有可控的墙体间隔。
   - 使剩余空间不足以达到最低房间数。
5. 对候选布局进行轻量评分：优先选择分布均匀、中心距离较大、没有全部挤在同一侧的布局。

每次完整布局最多尝试 20 次；单次布局内部最多尝试 100 个房间候选。达不到最低房间数时，丢弃整张布局并用下一个确定性的重试种子重新开始，而不是留下半成品地图。

### 第 3 步：建立房间连接图

房间是节点，候选连接是边。

1. 为每对房间计算连接权重，基础权重为两个房间边界最近点的曼哈顿距离。
2. 对穿过其他房间、过长或明显贴边的候选边增加惩罚。
3. 使用 Kruskal 或 Prim 生成最小生成树，保证所有房间至少连通一次。
4. 从未加入树的候选边中按概率加入 1–2 条额外连接，形成少量环路。
5. 给入口房和出口房之间保留至少一条不依赖单个特殊房间的可行路线，避免某个房间成为无法绕开的单点。

最小生成树是硬约束；额外环路是软约束。若在小地图上空间不足，优先保证全部房间连通，允许不加入额外环路。

### 第 4 步：挖掘过道

对每条房间图边：

1. 选择两个房间相对的边界点作为连接点，连接点应尽量靠近两房间的最近方向。
2. 生成两种 L 形路线：先横向后纵向、先纵向后横向。
3. 对路线评分，优先级依次为：不穿过第三个房间、不过度贴边、不产生不必要的重复挖掘、长度较短。
4. 随机选择得分接近的路线之一并雕刻墙体。
5. 如果两条 L 形路线都不合格，使用网格 BFS/A* 在墙体上寻找允许经过既有过道的替代路线。
6. 将新挖出的、且不属于任何房间矩形的地块记录为过道地块。

过道应与房间地板直接连通。房间内部保留为房间语义，即使过道入口进入房间后继续延伸，也不能把整间房间重新标记为过道。

### 第 5 步：指定房间角色

地图结构完成并通过连通性验证后，再确定房间角色：

- 入口房：从房间列表中随机选择靠近地图边缘但不贴边的房间；若存在多个候选，优先选择较小房间。
- 出口房：选择从入口房计算出的 4 方向最短路径最长的房间；优先选择大房间。
- 目标房：特殊敌人或 Boss 所在房间，必须是大房间且不能与入口房重合。
- 普通房：剩余房间，用于普通敌人、物品和路线分支。

入口和出口必须使用房间内部地板，不能直接放在过道中。若房间中心被特殊结构占用，则在房间内部按距离中心最近的可用格替代。

### 第 6 步：布置敌人和物品

地图结构与内容分离。先锁定入口、出口、目标房，再从房间容量中分配对象。

- 入口房不放置普通敌人，避免玩家出生即受攻击。
- 出口房不放置会阻塞出口格的对象。
- 普通敌人分散到至少 3 个不同房间，避免所有战斗集中在一间房。
- `defeatCount` 的目标数量为 5–10 时，生成器必须先计算可用房间格容量，再生成对象；容量不足应重新生成布局，而不是静默减少敌人。
- 特殊敌人放在远端大房间，房间至少保留 4 个可用地板格。
- Boss 放在最大的大房间中央区域；Boss 房至少有一条可进入路线，并保留足够的战斗空间。
- 第一版物品继续只放在房间内。过道中的伏击、陷阱和事件属于后续内容类型，不应通过随机地板位置临时实现。

## 5. 生成结果与数据边界

`FloorState` 继续以现有字段作为运行时最小接口：

- `width`、`height`
- `tiles`
- `visibility`
- `entranceIndex`、`exitIndex`
- `exitUnlocked`
- `objective`
- `enemies`、`items`

生成器内部新增一个不一定进入存档的 `MapLayout`：

```ts
type ConnectionKind = 'cycle' | 'branch' | 'chord' | 'shortcut';

interface RoomConnection {
  fromRoomId: number;
  toRoomId: number;
  kind: ConnectionKind;
  corridorId: number;
}

interface MapLayout {
  rooms: RoomLayout[];
  corridors: CorridorLayout[];
  connections: RoomConnection[];
  loopRoomIds: number[];
  entranceRoomId: number;
  exitRoomId: number;
  roomIdByCell: (number | null)[];
  corridorIdByCell: (number | null)[];
}
```

其中 `loopRoomIds` 的长度至少为 3，`connections` 记录回路边、支线边以及可选的中穿过道，不能用固定房间编号推断房间角色。

敌人 AI 需要在运行时判断当前位置所属房间，并在读档后保持同一张地图的房间边界。因此 `FloorState` 现在保存轻量的 `rooms` 和 `corridors` 元数据，不保存完整的生成器对象或函数索引；加入这些字段后存档版本同步升级，存档校验也会检查房间边界和过道格坐标。

地形语义与地块类型保持分离：

- `wall`：不可通行地形。
- `floor`：普通可通行地形，可能属于房间或过道。
- `entrance`、`exit`：在普通地板上叠加的特殊地标。
- 房间/过道信息：由 `MapLayout` 或生成阶段的区域索引提供，不新增 `roomFloor`、`corridorFloor` 两种可通行地块。

## 6. 失败处理与硬约束

每张地图在交给游戏状态前必须通过验证器。硬约束包括：

1. 外围一圈仍为墙。
2. 房间数量和大小分类达到当前 `MapProfile` 的最低要求。
3. 房间矩形互不重叠，并满足最小墙体间隔。
4. 所有房间和所有可通行地块都能从入口使用 4 方向到达。
5. 入口和出口不同，且出口可达。
6. 出口位于房间内，不位于过道。
7. 目标房符合楼层目标要求。
8. 敌人和物品不重叠、不占用入口/出口，并有足够可用地块。
9. `defeatCount` 的普通敌人数量不少于目标数量。
10. Boss 房满足最小战斗面积和至少一条进入路线。

软约束包括房间分布均匀、过道长度、环路数量和入口出口距离。软约束不满足时可重新生成；重试次数耗尽后使用一个固定的保底布局，保底布局也必须通过全部硬约束。

保底布局应是手工定义的 6 个房间和连接关系，而不是“随机失败后直接开一块 8×8 地板”。这样即使随机生成器出现异常，玩家仍能得到符合房间/过道设计的地图。

## 7. 与现有代码的迁移顺序

### 阶段 A：低风险过渡

保留 `rot.js` `Digger`，但在生成后立即构建 `MapLayout`：

1. 使用 `getRooms()` 生成 `RoomLayout`。
2. 通过“地块是否落在任一房间矩形内”分类房间地板。
3. 其余可通行地块分类为过道。
4. 根据房间中心和 4 方向 BFS 验证连通性。
5. 增加大/小房间识别、房间角色和生成测试。

这一步可以先让对象布置和测试使用房间语义，而不改变玩家可见的地形接口。

### 阶段 B：切换到目标生成器

新增独立模块，例如：

- `src/world/layout.ts`：布局类型和区域索引。
- `src/world/room-generator.ts`：房间放置。
- `src/world/corridor-generator.ts`：房间图和过道挖掘。
- `src/world/map-validator.ts`：硬约束验证。
- `src/world/generate.ts`：编排目标、布局和内容生成。

`generateFloor` 只负责组织阶段，不再直接同时处理挖图、放房间、放敌人和放物品。每个阶段都接收显式输入并返回结果，方便单测和复现指定 seed。

## 8. 测试与验收标准

在现有 `generate.test.ts` 基础上增加：

- 相同 `seed + floorNumber` 生成的房间、过道、入口、出口和内容完全一致。
- 不同 seed 通常产生不同房间布局，而不只是对象位置不同。
- 连续抽样至少 500 个 seed，所有地图均通过硬约束验证。
- 每张地图的所有可通行地块都能从入口通过 4 方向 BFS 到达。
- 房间无重叠，房间数量、大房间数量和尺寸都符合配置。
- 每条房间图边都有实际过道连接；没有只挖到墙边的断头连接。
- 出口始终位于与入口不同的可达房间。
- 特殊敌人始终位于大房间；Boss 始终位于 Boss 大房间。
- `defeatCount` 在所有抽样 seed 下都生成不少于目标数量的普通敌人。
- 敌人、物品、入口和出口没有位置重叠。
- 生成失败时会重试并最终返回符合约束的布局，不会返回半成品地图。

完成这些测试后，地图生成才算从“能生成地板”升级为“能生成可解释、可验证、可扩展的房间—过道地图”。

## 9. 后续可扩展方向

在不改变房间图核心的前提下，可以继续增加：

- 房间主题：祭坛、宝箱、商店、事件、精英战。
- 过道主题：普通过道、窄道、陷阱、伏击点、分叉路。
- 房间门和锁：把门作为房间图边上的状态，而不是把墙体随机改掉。
- 大关配置：通过 `MapProfile` 调整房间比例、过道环路、目标房距离和 Boss 房面积。
- 路线评分：根据入口到出口的房间数、战斗房数量和资源房数量控制楼层节奏。
- 地图分析数据：记录房间图、最短路径长度、分支数和环路数，用于调试和难度平衡。

这些内容都应建立在“先生成房间图，再生成地块和内容”的顺序上，避免将玩法规则重新散落到单个随机坐标判断中。
